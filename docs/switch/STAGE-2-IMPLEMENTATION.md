# Complete-packet intake — implemented checkpoint

4 November 2026. This checkpoint covers executable Stage2 work, not the completed correction/review/share workflow or a contest submission. [Frozen contract](STAGE-2-CONTRACT.md).

## What now works

- The assistant stages one bounded attachment using the configured job and fixed loopback service. Private tool configuration version1 retains the original two read tools. Version2 adds only `delivery_stage_receipt`, with an operator-configured incoming folder. The client refuses outside paths, traversal, symlinks in any component, hard links, FIFOs, empty/oversized/changed files and arbitrary request options. No model tool can confirm a packet, save a human assessment or authorize sharing.
- The local desk shows received files and source references, distinguishes new/earlier/unavailable receipts, and proposes available new files as a selection. The lead must include every file retained in this revision. Nothing is silently merged.
- Packet preview shows added, replaced, removed and unchanged filenames, excluded receipt count, total bytes and stale-review implications. The lead explicitly confirms comparison with the conversation and complete selection. Source IDs remain **unverified provenance**; they are not trusted chat identity merely because an assistant supplied them.
- An all-or-nothing backend confirmation uses exact revision/input hash, manifest digest and a stable operation key. The digest includes selected receipt identities plus all receipts present during preview; later arrivals require a fresh preview. Repeat confirmation returns the committed historical result before checking later revisions. Reusing a key with different inputs conflicts.
- Native file inspection runs outside the SQLite write transaction. Copies are checked against actual receipt hashes. Unsupported/blocked candidates refuse the entire packet and retain the old packet/review. Successful registration, project body, packet manifest and operation receipt commit together. Changed contents invoke inherited stale-review/proposal history; identical contents preserve IDs, revision and review. Existing exports remain frozen.
- The integration schema migrates1→2 transactionally without changing legacy project/export layouts. Original data was backed up through SQLite's backup API before activating the update. A lost commit acknowledgement is reconciled against the stored operation. If reconciliation also fails, possibly registered new bytes and old originals are retained; no unknown outcome is reported as success.
- Pending receipts are separate from current evidence and prevent a ready delivery status. Previously considered staged-byte damage does not falsely damage independently verified committed originals. Legacy duplicate filenames cannot collapse into a false unchanged-packet result. Deleting a room-linked project is refused until explicit room archival/receipt retention support exists.

## Retry and bounded operation

The browser retains the same confirmation key/body through an interrupted reply or refresh, including a remount in the same browser session. A lost reply asks the operator to reconcile that confirmation, rather than silently generating another key. A successful API response alone does not produce the completion announcement: the authoritative project and received-file context must refresh first.

The CLI has a10-second budget for an unclosed stdin pipe as well as its64KiB argument budget. It accepts a closed JSON input stream, returns structured failures, and never prints credentials or arbitrary upstream error bodies. The published revision schema includes the runtime upper bound. Backend/client token character sets now agree. MCP accepts an absent/null/empty first-page cursor; it does not issue pagination cursors for its small static tool list.

Retained staging remains limited to60 receipts/job and100MiB total, including considered receipts. Stage2 does not silently delete history to make room. Reaching that limit requires an explicit operator action; a retention/cleanup workflow is still unfinished. This is a lead-operated local desk, not an always-on hosted service, multiuser auth system, OS sandbox or power-loss durability certification.
