## Context service methods

- `read_project(project_id)` local-only returns `{job_id, source_revision, input_hash, context_epoch, questions}` or null. Questions include `{question_id,requirement_id,question,source_ref,source_revision,input_hash,source_hash,file_ids,evidence,legacy,state,active_context,replies,latest_resolution}`. Replies include `{reply_id,source_ref,reported_speaker,text,text_hash,created_at}`; provenance is always explicitly unverified. States are `pending`, `resolved`, `superseded`. No question/reply text is copied to the agent status projection.
- `propose_question(job_id,binding,operation_key,*,expected_revision,expected_hash,expected_epoch,requirement_id,file_ids,question,source_ref)`. New questions require current approved checklist, exact project revision/full hash/job epoch, unique registered candidate IDs, and current requirement. Compute provisional `evaluate_selection` evidence on backend; sanitize literal expectations and manual instructions as existing preview does. Store original full hash plus source-only anchor, selection and immutable evidence. No assessment/scope change. Return operation envelope with committed currency and `{question_id,context_epoch,assessment_saved:false}`.
- `record_reply(job_id,binding,operation_key,*,question_id,question_input_hash,source_ref,reported_speaker,text)`. Bind to the immutable original question hash, not current project. Late replies may be stored as historical and cannot automatically apply. Same question/source_ref with different speaker/text conflicts; identical receipt does not bump epoch twice. Return envelope with `{reply_id,question_id,context_epoch,state,provenance:'unverified'}`. Any new reply to a current resolved question reopens its hold; superseded questions stay historical.
- `resolve(job_id,binding,operation_key,*,question_id,expected_revision,expected_hash,expected_epoch,action,covered_reply_ids,used_reply_ids,reason)`, LOCAL ONLY. `action` is `accept`, `dismiss`, `withdraw`. Validate full current currency and epoch in transaction. `covered_reply_ids` equals ALL current reply IDs for this question, including empty for unanswered dismissal. Accept requires nonempty used subset; legacy questions are dismiss-only. Historical questions cannot be adopted in this stage—create an explicit new current question/reference instead. Dismiss/withdraw use no used IDs and require reason. Acceptance replaces this question's active context basis and invalidates review; accepting the same used IDs/hashes/source preserves an identical active basis. Dismissing a follow-up keeps an earlier accepted basis, labelled visibly. Withdraw explicitly removes that basis and invalidates review. Store immutable resolution and exact covered/used IDs. No scope approval, human disposition or share authorization is saved.
- `record_legacy(db,job,project,blocker_id,requirement_id,message,original_revision,original_hash)`: compatibility hook used inside the existing foundation proposal operation; creates a labelled dismiss-only question and advances epoch once. New exposed agent tools use `propose_question`, not this helper.

Agent question/reply/source strings bounded (question1000chars, reply2000chars, source256chars, speaker120chars, reason1000chars; printable text with newline/tab allowed for reply/reason). ≤100questions/job using existing blocker limit, ≤200reply receipts/job, ≤1100resolution events/job, existing1000operation/64KiBresult budgets apply. Stable operation replay after binding precedes current-version checks. New mutations/result/epoch/project changes commit atomically with post-mutation result currency; do not reuse `_operation`'s pre-apply hash for acceptance. Local source-change hook never overwrites preserved histories.

## API and interface

- Agent/local POST `/delivery/jobs/{job}/questions`: operation_key, expected_revision, input_hash, expected_context_epoch, requirement_id, file_ids, question, source_ref.
- Agent/local POST `/delivery/jobs/{job}/questions/{question}/replies`: operation_key, question_input_hash, source_ref, reported_speaker, text.
- Local GET `/projects/{project}/delivery-context`: `{enabled,job:read_project_or_null}`; persisted state remains visible if disabled.
- Local POST `/delivery/jobs/{job}/questions/{question}/resolve`: operation_key, expected_revision, input_hash, expected_context_epoch, action, covered_reply_ids, used_reply_ids, reason, `confirmed_reviewed:true` (strict true).
- Agent status adds safe `context_epoch`, `pending_context_count`, compact question IDs/states/requirement IDs/original hashes, never private resolution reasons/raw text. Pending context has priority over ready state.

One inline review card lists questions, backend provisional findings, source references, unverified replies, active earlier context and history. For each pending current question, lead selects used replies, enters reason and explicitly checks sources before Use/Dismiss/Withdraw. “Changes checklist” only navigates the existing editor; IT DOES NOT resolve anything or clear the hold. A real edit supersedes old questions and makes checklist/reviews stale through existing rules; fresh checklist confirmation remains required. No separate scope-change state machine.

Component props: `{project:Project,disabled:boolean,onCommitted:()=>Promise<unknown>,onBusy:(boolean)=>void,onChecklist:()=>void}`. Key by project. Keep stable operation payload/key across ambiguous replies/remount; clear only known definite refusal, refresh authoritative context/project before success. Surface historical questions without active resolution controls. Parent blocks navigation/other mutations during local context operation, as for packet intake. Display disabled-integration safety holds without suggesting the agent is online.
